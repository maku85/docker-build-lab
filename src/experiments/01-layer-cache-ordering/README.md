# 01: Layer cache ordering

## Question

After changing a source file that is **not** `package.json`, does the
`RUN npm install` layer stay a cache hit?

- `naive`: `COPY . .` then `RUN npm install`. The source change busts the
  `COPY` layer, and every layer after a busted one rebuilds, so `npm install`
  re-runs.
- `ordered`: `COPY package.json` then `RUN npm install` then `COPY . .`. The
  source change busts only the final `COPY`; `npm install` sits above it and
  stays cached.

## Fixtures

One tiny app (`is-number`, `is-odd`), two Dockerfiles, generated by
[`gen.ts`](./gen.ts). Base image `node:22-alpine` (pinned by tag).

Per variant: remove the app image → cold build (`--no-cache`) → overwrite
`index.js` → warm rebuild. The warm rebuild is the measurement. `--no-cache`
forces every step on the cold build without pruning the machine's global
BuildKit cache.

## Run

```bash
npm run exp:01
```

Needs a working Docker daemon with BuildKit (Docker 23+). The cold builds pull
the base image and the two npm packages once.

Output → `results/01-layer-cache-ordering/<timestamp>/`:

- `comparison.txt`: the table
- `build-log/<variant>.cold.txt` / `.warm.txt`: verbatim `--progress=plain`
- `context/<variant>/`: the exact generated build context
- `summary.json`: parsed per-step records

## Results

Docker 29.4.0, buildx 0.33.0, Apple M3 Pro. **Confirmed.**

| variant | warm `npm install` | warm cached | warm rebuilt | image |
| --- | --- | --- | --- | --- |
| `naive` | re-run | 1 / 4 | 3 | 171.6 MB |
| `ordered` | CACHED | 3 / 5 | 2 | 171.6 MB |

- `naive`: touching `index.js` busts `COPY . .`, and every step below a busted
  step rebuilds, so `RUN npm install` re-runs. Only `WORKDIR` stays cached.
- `ordered`: the change busts only the final `COPY . .`. `RUN npm install` sits
  above it and stays a cache hit; the rebuild does the last `COPY` and the image
  export, nothing else.
- Both images are the same size (same final filesystem). Ordering changes *what
  rebuilds*, not the result.

### Note on "cold"

The BuildKit cache is global and persistent. `--no-cache` stops a build
*reading* the cache but it still *writes* entries, and a later build with the
same content can hit an entry left by a previous run. The first version of this
experiment used a fixed marker string and got a spurious cache hit on `naive`
from an earlier run. The fix: a run-unique token in `index.js` so both the cold
state and the changed state are genuinely novel.
